## Batch 2A: counting pace

### 2A-1 Bug: the "Running count at table pace" rung passes at any speed

**The threshold.** A run is at table pace when its per-card pace is **at most 576 ms**, which is a
deck in 30 s or faster. The code already defines table pace this way in three places:
- `classifySpeed` (`countSpeed.ts`): `<= 30 s` per deck is `'table-ready'`, and that is the
  benchmark counters cite (docs/research/2026-07-21-priority-list.md item 6, pain-points §143).
- `tierStartIntervalMs('table-ready')` = `floor(30000/52)` = **576 ms**. That is the Timed
  Challenge's table-ready interval, i.e. "the drill's table-pace interval".
- The "Full shoe" achievement (`habits/achievements.ts:409`) already says "table-ready pace (a deck
  in 30 s or faster)". It tests `classifySpeed(perCard*52/1000) !== 'learning'` on
  `countRunPerCardMs`, so the rung and the achievement will mean the same thing.

**Code (`src/drills/countSpeed.ts`, owned):**
- `export const TABLE_PACE_MS = tierStartIntervalMs('table-ready')` (576).
- `export function isTablePace(perCardMs: number | undefined): boolean`: `perCardMs > 0` and
  `classifySpeed(secondsPerDeck(perCardMs, 1)) !== 'learning'`. This is the same predicate Full shoe uses.
- `CountRunPace` gains `group?: 2 | 3`. `countRunPerCardMs` divides an auto (non-eyes-free,
  non-manual) run's `intervalMs` by `group ?? 1`, because the flash timer runs once per *group*
  (`CountDrillView.tsx:671`). As things stand, a 3-card group at 800 ms is recorded as 800 ms a card
  when it is really 267 ms. Eyes-free (`elapsedMs / cards`) and manual (`meanTapMs`) are unchanged.
  Table mode is unchanged too: its timer is `interval × cards in the round`, so the per-card pace
  is already `intervalMs`, and table rows never get `group` written.

**Code (`src/drills/fluencyGate.ts`, owned):**
- `CountRunLike` gains `intervalMs`, `elapsedMs?`, `eyesFree?` and `group?` (the stored row already
  has all of them, so `nextStep.ts` keeps compiling unchanged because it passes whole rows).
- `isQualifyingRun` = the current checks **and** `isTablePace(countRunPerCardMs(run))`.
- `export const FLUENCY_RULE_TEXT = 'a deck or more, at a deck in 30 s or faster'`. Copy that other
  screens can quote (see "Requests" below).
- Header comment updated: the rule now names pace.

**Storage write (`CountDrillView.tsx` finishRun ~1530, owned):** add `group` to the row when
`!tableRun && countGroup > 1`. This is a new optional field on `Stats.countDrill.history[]` in
`src/store/types.ts`, which is a **shared file, add-only**. Old rows have no `group` and are
read as group 1. That is conservative: an old fast group run reads as slower than it was, never
faster.

**Existing too-slow passes: they stop counting.** Nothing is migrated or deleted. Fluency is
recomputed from history on every read, so stored runs slower than 576 ms a card simply stop
qualifying. Someone who passed the rung at 800 ms will see it un-pass. Home's progress drops
to however many table-pace deck runs they have, and the count drill becomes the current step
again. The rows are still in Stats, the streaks and the achievements. The step now means what
its label says.

**Count-drill result screen (owned):** under the existing `RungProgressLine`, add one line for
paced, graded deck runs that miss the pace: "Too slow to count toward the step: 800 ms a card. Table
pace is a deck in 30 s (576 ms a card or faster)." There is a matching line for runs that are too short. Today a
user cannot tell why a correct run did not move the rung. Pure helper `rungMissReason(run)` in
`fluencyGate.ts` returns `'manual' | 'selfReport' | 'short' | 'slow' | null`.

**Unit tests (`fluencyGate.test.ts`, `countSpeed.test.ts`):**
- 52 cards at 576 ms qualifies, and at 577 ms does not. This is the exact boundary, so
  mutation-check both `<=` and the predicate.
- 800 ms (the old default) does not qualify. A group-of-3 run at 1500 ms (500 ms a card) does.
- An eyes-free row with `elapsedMs/cards` = 700 does not qualify even when `intervalMs` = 300 (the gap).
- `countFluency` over 5 correct 800 ms runs → `judged: 0`, `fluent: false`, which is the
  "existing passes stop counting" ruling as a test.
- `rungMissReason` returns each case.
- `countRunPerCardMs` with `group` divides, eyes-free and manual ignore `group`, and a table row has none.

**Fixture fallout.** Test data seeds count runs at 700/800/1000 ms that are *meant* to be
qualifying. Each one changes **only its `intervalMs` number** (to 550). No assertions change.
- `src/ui/screens/ladderFixtures.ts:19` (`runs()`, 700). Not on either track's list; test-only.
- `src/ui/screens/nextStep.test.ts` (one inline 700 row). Test of a T1 file; seed number only.

### 2A-2 Pace steps up gradually, gated on accuracy

Today: Easy first run writes `countIntervalMs: 2000` (`hiLoAid.ts EASY_FIRST_RUN`), and the user
then has to work out alone how to get to a pace that counts. The new 576 ms rule makes that gap
wider.

**Pace steps (new file `src/drills/countPaceRamp.ts`, owned):**
- `PACE_STEPS_MS = [2000, 1500, 1100, 800, 550]`, five steps. Step 1 is the Easy first run's pace,
  and step 5 is the first value at or under `TABLE_PACE_MS` (550 = 28.6 s/deck). The middle steps
  follow the geometric ramp `rampIntervalMs(i, 2000, { decay: (576/2000)^(1/4) ≈ 0.733, floorMs:
  576 })` = 2000, 1465, 1073, 786, 576, rounded to a 50 ms grid, with the last one taken down to
  ≤ 576. A unit test pins that relationship, so the steps are derived from `rampIntervalMs`
  instead of being picked by hand.
- `stepOfPace(perCardMs)`: the fastest step whose ms ≥ the pace (a 1300 ms run is an attempt at
  the 1500 step; anything slower than 2000 counts as step 1; anything ≤ 550 is step 5).
- `rampHistory(countDrillHistory)` → `{ tier: StepId, correct }[]` over graded, auto, visual rows of
  ≥ 52 cards (not manual, not self-report, not eyes-free; see Assumptions).
- `paceRampStatus(history, gateOpts)` → `{ step: 1..5, ms, judged, right, next: { ms, need } | null,
  change: 'advanced' | 'held' | 'eased' }`, built on `computeUnlockedTier`.
- `rampChangeAfterRun(historyBefore, newRow)`: before and after, the same way the Timed Challenge
  does it (`CountDrillView.tsx:1500`).

**Gate (`src/drills/competenceGate.ts`, owned):** generalise without changing current behaviour:
`computeUnlockedTier<T extends string = SpeedTier>(history, opts?: GateOptions & { order?: readonly T[] })`,
`order` defaulting to `SPEED_TIER_ORDER`, plus a `tierAbove` overload the same way. The existing
Timed Challenge callers and every existing test stay as they are. The ramp uses
`{ windowSize: 5, minAttempts: 3, advanceThresholdPct: 80 }`, so stepping up takes 3 of 3 right at a
step, or 4 of the last 5. The gate's fixed 3-misses-in-a-row ease drops one step.

**Setting:** `Settings.drill.countPaceRamp?: boolean`, absent = on. Label "Step the pace up as I get
it right". It is drawn in the count drill's **Pace** options group, under "Time per card"
(`CountDrillView.tsx` ~2400). Adding it touches the **shared** `src/store/types.ts` (add field) and
**shared** `src/ui/settingsRegistry.ts` (append `'countPaceRamp'` to the drill-options list, no
reordering).

**Behaviour (`CountDrillView.tsx`, owned):**
- When the ramp is on and a ramp-eligible run finishes with the step advanced or eased, the drill
  writes `countIntervalMs` = the new step's ms (through `updateDrill`), so the next run deals at it.
  When nothing changes, it writes nothing. The user can still move the "Time per card" stepper
  freely. The gate reads the step from what was actually dealt, so a hand-set faster pace is never
  pulled back unless three runs in a row miss.
- **Setup screen** (under the stepper, when the ramp is on and the run is visual/auto): "Pace step 3
  of 5 · 1100 ms a card. 1 of 3 right here so far: 3 right (or 4 of your last 5) unlocks 800 ms."
  At step 5: "Table pace: deck runs at this pace count toward the step." The beginner sees which
  step they are on and what unlocks the next. Hidden in eyes-free, manual, Countdown and Timed Challenge.
- **Result screen:** "Pace up: next run deals at 800 ms a card (step 4 of 5)." or "Eased back to
  1100 ms after three misses in a row." or (held) "1100 ms: 2 of 3 right here." This is one
  line, shown with the existing `RungProgressLine`.
- `EASY_FIRST_RUN` is unchanged (2000 ms = step 1), so the Easy first run is the ramp's first attempt.

**Unit tests (`countPaceRamp.test.ts`, `competenceGate.test.ts`):**
- The steps match the derived ramp, the last step ≤ `TABLE_PACE_MS` and the one before it is > it.
  Mutate `PACE_STEPS_MS[4]` to 600 and the test must fail.
- `stepOfPace` boundaries: 2000 → 1, 1999 → 2, 1500 → 2, 551 → 4, 550 → 5, 300 → 5, 2500 → 1.
- 3 right at 2000 → advanced to 1500; 2 right + 1 wrong → held; 4 of 5 → advanced; 3 wrong in a
  row at 1100 → eased to 1500. Manual, eyes-free, self-report and 26-card rows are ignored (each
  is a single-row mutation that changes the result).
- `computeUnlockedTier` with a custom `order` behaves the same as the default over the
  `SPEED_TIER_ORDER` alphabet. This is a property test over random histories, compared against the
  unchanged default.

**e2e (`e2e/count-pace-ramp.spec.ts`, new):**
- Seed two right runs at 2000 ms, open setup and check "Pace step 1 of 5 … 2 of 3 right". Do one
  real right run (`?e2e=1`, fast interval patch so the spec is short; the ramp reads seeded rows),
  then check the result says "next run deals at 1500 ms" and the reopened setup's stepper reads
  1500ms.
- With the ramp off, the same flow keeps the stepper at 2000ms.
- A seeded 800 ms right run shows the "Too slow to count toward the step" line, and Home's count
  rung does not move (read via `rungProgressLine` text on the result screen).

**Visual:** count setup (step line), result (pace-up line and too-slow line), Options › Pace with
the new toggle, all at 375×812 headless WebKit.

### 2B-2 One-line "why" under basic-strategy misses (Flashcards, Mastery)

**New pure module `src/ui/screens/drills/missWhy.ts` (owned):**
`missWhy(cellId, rules): string | null`. It is built from `regionRuleFor` (section, rows, ups,
action) and `bustLine(up, rules)` (read-only import from `playMissReason.ts`, which is not
edited). It picks one principle by section, action and dealer band, then appends the bust line:
- dealer 2–6, stand/double: "The dealer's 2–6 are bust cards: let them bust." + bustLine
- dealer 7–A, hard 12–16 hit: "A 7–A usually makes 17 or more, so a stiff hand has to draw." + bustLine
- hard ≤ 11 hit: "No single card can bust you, so take one."
- double, any band: "You're the favourite here, so get more money out while the dealer is weak or
  your total is strong."
- split A/8: "Two aces or two 8s start better apart: 16 is the worst total there is."; other splits:
  "Each card starts a better hand on its own than the pair does together."
- never split 10s/5s: "Twenty is already strong. Two 10s apart are worth less." / "5,5 is a 10: double it, don't split it."
- surrender: "You lose more than half the time here, and surrender gives back half your bet."
- soft hands: "A soft hand cannot bust on one card, so the draw or double is cheap."
- otherwise: bustLine alone.
Written in at most 2 sentences.

**`drillMiss.ts` (owned):** `DrillHandResult` gains `why?: string`. `withMissDetail` fills it for
flashcard and mastery misses only (same guard as `withRegionRule`).

**Render:** new `src/ui/screens/drills/MissWhyLine.tsx`, the `MissHistoryLine` pattern. It is a

## Risks

- **The rung un-passes for current users**, Jack included, if his runs were at 800 ms. This is
  intended (see the ruling) and the result screen explains it. Home will put counting back as the step.
- **Eyes-free runs rarely reach table pace.** Speech plus the ≥300 ms gap is around 700+ ms a card,
  so car practice mostly won't move the rung. That matches the label and Full shoe's existing C6
  rule, but it is the assumption most likely to be overturned (see A3).
- Countdown-mode rows are stored the same way as ordinary runs (no marker), so a Countdown run at
  table pace counts toward the rung and the ramp, exactly as it counts toward fluency today. I am
  leaving that as it is and noting it.
- `countRunPerCardMs` honouring `group` changes Stats' best-run ranking and Full shoe for *new* group
  runs. That is correct, but it is a visible change.
- e2e seed edits in shared specs could conflict with Track 1's edits to the same specs. The diffs are
  one-number seeds, so a conflict is trivial to resolve.
- A Term inside a label or in a timed prompt: a tap during a shot-clock question opens the sheet
  without pausing the clock. That is accepted, because the chips are read before answering.
- The ramp writing `countIntervalMs` could fight a hand-set pace. It only writes on an advance or
  an ease, it says so, and the toggle turns it off.

## ASSUMPTIONS

- **A1 Table pace = ≤ 576 ms a card (`TABLE_PACE_MS = tierStartIntervalMs('table-ready')`, a deck in 30 s),
  judged with the same predicate as the Full shoe achievement.** It is the code's own definition and the cited benchmark.
- **A2 Existing too-slow passes stop counting**, with no migration. Fluency is recomputed from
  history, and old rows stay in Stats.
- **A3 Eyes-free runs are judged on their measured pace (`elapsedMs / cards`)**, with no exemption. Flip:
  one line in `isQualifyingRun`.
- **A4 Old rows have no `group`** and are read as single cards, which is conservative.
- **A5 Ramp steps 2000 / 1500 / 1100 / 800 / 550 ms**, derived from `rampIntervalMs`, with gate options
  window 5, min 3, 80%, and 3 misses in a row to ease. On by default (`countPaceRamp`), visual auto runs only.
- **A6 The ramp sets "Time per card" for the next run** only when it advances or eases. It never locks the stepper.
- **A7 Learn Hi-Lo is shown** once, when basic is passed and the count rung isn't, so it "waits" past
  basic strategy even for someone who already did a count run early. It is never a lock.
- **A8 Worked examples are inline cards on the setup screen**, once per drill (first visit with empty history),
  then a permanent "How it works" fold. They are gated in e2e on `?intro` like ChartIntro.
- **A9 The glossary sheet has no backdrop**, sits at a fixed bottom, and holds one at a time. Terms are wrapped
  only where the word already appears, with no added copy.
- **A10 The "Why?" line is collapsed by default** (one summary line), Flashcards and Mastery only.
