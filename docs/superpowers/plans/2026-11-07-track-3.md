## 3A.1 Resume a shoe after iOS closes the app

### Behaviour

- **What comes back:** the table the page lost. If the page dies while Play is open (an iOS eviction during a call or
  a Maps check, a crash, or a reload), the next Play mount in the next page load restores the table as it stood at
  the last round boundary. It restores the same shoe order and position, the count (running count, true count, the
  Rewind trail, side count), bankroll, round number, the settled round still on the felt, graded events, the session
  row and committed counts, any owed count check, the In/Out toggle, the side-bet chip, an uncalled dealer error, and
  the dealer-error and side-bet tallies.
- **What does not come back:** a table left by choice.
  - **End**, the end of the session, discards it (the brief's "finished").
  - **Leaving Play for Home, Drills, Stats or the profile editor** discards it, as today (D3: those exits "never
    promised a way back"). Play to Settings keeps it, in memory as today and now also on disk, so the Settings round
    trip survives an eviction too.
  - **A new table** discards it. That covers a profile or rules edit, a bankroll reset, the losing-shoe toggle,
    anything that bumps App's `tableEpoch`, and the new **New shoe** button on the resume note.
  - **Expiry:** saved more than **12 h** ago (ASSUMPTION A1).
  - A saved table that does not decode, or carries the wrong version, is dropped silently. It is disposable state,
    so it is not quarantined.
- **Mid-round death:** the table resumes at the start of the round that was cut off. The shoe order is exact, so
  that round is dealt again from the same cards (ASSUMPTION A3). The resume note says where the count stands.
- **On a resumed mount,** a note sits under the topbar until the next deal or until it is dismissed:
  "Shoe resumed at round 23 (saved 14 min ago). The count is where round 23 left it." It has a **New shoe** button.
  `data-testid="resumed-shoe"`.

### Persisted shape: `bjtrainer.tableResume.v1` (one key, JSON)

```ts
// src/ui/tableResume.ts
export const TABLE_RESUME_KEY = 'bjtrainer.tableResume.v1';
export const RESUME_MAX_AGE_MS = 12 * 60 * 60 * 1000;

export interface SavedTable {
  version: 1;
  /** Epoch ms of this write. Expiry is measured from it. */
  savedAt: number;
  /** resumeKeyFor(profile, settings): profile id + profile content minus bankrollNow, + the losing-shoe flag. */
  key: string;
  /** This session's start stake, so the restored GameConfig and report delta are the session's, not today's bankrollNow. */
  bankrollStart: number;
  /** The losing shoe's script seed; absent for a fair shoe. */
  scriptSeed?: number;
  /** Same fields as tableKeep's KeptSession: id, committed, sideCommitted, peeks, paced, storedBankroll. */
  session: KeptSession;
  game: EncodedResume;
}
```

`EncodedResume` is `GameResumeState` (below), with every `Card` written as a 2-character string such as `'As'`,
`'Td'` or `'9c'` (T stands for 10). Cards are encoded in hands, dealer cards, the trail and the shoe. Events are
stored as they are (`GradedEvent` is plain JSON).

```ts
// src/engine/game.ts (exported type, beside the class)
export interface GameResumeState {
  phase: 'idle' | 'settled';
  /** Fair shoe: the cards still to come, in order; how many were dealt; where the cut sits.
   *  Rigged (losing) shoe: only how many of the current pass were dealt (rebuilt from scriptSeed). */
  shoe: { kind: 'fair'; upcoming: Card[]; dealt: number; cut: number } | { kind: 'rigged'; dealt: number };
  runningCount: number;
  trail: Card[];
  sideRanks: number[]; sideSuits: number[];          // SideCounter's two arrays
  dealerCards: Card[]; holeRevealed: boolean;
  seats: Seat[]; playerSeatIndex: number; active: number;
  bankroll: number; roundNo: number; handsPlayed: number;
  events: GradedEvent[];
  countCheckDue: boolean; askRc: boolean; askTcToo: boolean; countCheckPromptCount: number;
  shuffledLastRound: boolean; insuranceNet: number | null;
  dealerError: DealerError | null; foulVerdict: FoulVerdict | null; missedDealerError: DealerError | null;
  dealerErrorTally: DealerErrorTally; dealerMistakesUsed: boolean; dealerMistakesTrainingUsed: boolean;
  toggleIn: boolean; lastIn: boolean;
  sideOn: boolean; sideDecisions: SideBetDecision[]; sideTally: SideTally;
}
```

`restoreResume` forces `countCheckOpen = false`, so an owed check that was being asked when the page died is
asked again at the next Deal. It sets `botActionLog = []` and `dealOrder = []`, so nothing is re-narrated or
re-animated. `sideOpen` and `sidePlayerCards` are always null at a boundary. The RNG streams (bot mistakes,
dealer errors, the cut placement of future shoes and the shuffle of future shoes) restart from a fresh seed. That
changes nothing observable, because nobody knows what the next shoe would have been.

Size: an 8-deck shoe is about 1.3 KB of cards. Events run about 250 B each and about 3 per round, so 100 rounds is
about 80 KB. Unit test U3 bounds 200 rounds under 300 KB. Risk R2 covers a cap.

### When it is written and cleared

| Moment | Action |
|---|---|
| `persistSession(false)` writes Stats (every settled round, every answered count check) | `saveTable()` in the same task, right after `saveStats`. The snapshot's `session.committed` is then always what Stats hold. |
| Between rounds, a change Stats don't see (In/Out toggle, side chip, Foul called) | The between-rounds effect calls `saveTableIfChanged()`, keyed on `roundNo / events.length / bankroll / isIn / sideOn / foulVerdict / countCheckDue / tally`. |
| Mount of a restored or kept table | `saveTable()` in the mount effect. This keeps StrictMode's simulated unmount and remount harmless. |
| Mount of a fresh table (roundNo 0, not restored, not kept) | `clearSavedTable()`. This covers every epoch remount: profile apply, bankroll reset, losing shoe, New shoe. |
| `endSession()` | `clearSavedTable()`. |
| `newShoe()` | `closeDealerError`, `persistSession(true)` (the row is finalised, as End does, but with no report), `clearSavedTable()`, then Table calls `tab.applyProfile(null)` to remount. |
| `noteNavigation` drops the kept table (Play to anywhere but Settings; Settings to anywhere but Play) | `clearSavedTable()`. |
| Mid-round (phase `player` or `insurance`) | Never written. The last boundary stands. |

**Read once per page load.** `peekSavedTable(key, now)` reads storage only for the page's first Table mount
(module flag). It caches the decoded `{ playGame, session, savedAt }`, so React's double render sees one object.
The mount effect calls `markTableMounted()`. Every later mount in the same page is in-app and is decided by
tableKeep and the fresh-mount clear. This rule is what stops an epoch remount, such as a bankroll reset, from
resurrecting the old snapshot: the new tree renders before the old one's cleanup runs.

### Chip display design

Pure module `src/ui/chips.ts`:

## 3B Rust checks (plan only; implement after rebasing on main once Track 1 is merged)

### Rule (owner's)

- First re-test 14 days after the pass. Each re-test passed in a row pushes the next one out:
  `RUST_INTERVALS_DAYS = [14, 30, 60, 120]`, staying at 120 after that.
- A failed re-test drops the interval back to 14 days and marks the rung as needing work.
- "If not practised": practice on the rung's skill restarts the clock. The re-test comes due `interval` days after
  the later of the last proof and the last practice. A rung drilled every week therefore never goes rusty, and a
  rung left alone does.
- Due moments use the spaced-repetition convention, 4am local on the N-th calendar day. This reuses
  `spacedRepetition.ts`: a new exported `dueAfterDays(now, days)`, which `scheduleDueAt` then calls, so there is one
  implementation.

### Data model: `bjtrainer.rust.v1`

```ts
// src/drills/rust.ts (new, pure + its small store)
export const RUST_KEY = 'bjtrainer.rust.v1';
export const RUST_INTERVALS_DAYS = [14, 30, 60, 120] as const;

export type RustRung = 'basic' | 'count' | 'tc' | 'deviations' | 'betramp' | 'play';   // 'repair' follows 'basic' (A11)

/** Monotone counters (or dated-row tallies) a re-test is judged on: what was added since `baseline`. */
export interface Evidence { n: number; right: number; /** dated rungs: per-part counts (tc: deck and tc) */ parts?: Record<string, { n: number; right: number }> }

export interface RungRust {
  /** 0 -> 14 days, 1 -> 30, 2 -> 60, 3 -> 120. */
  step: number;
  /** Epoch ms the rung was last proven: first seen passed, or a re-test passed. */
  provenAt: number;
  /** An open re-test: the moment it came due, and the evidence counters then. */
  retest?: { from: number; baseline: Evidence };
  /** A failed re-test: the rung reads not passed until a fresh re-test passes. */
  needsWork?: true;
  /** Last re-test outcome, for the copy ("passed its 30-day re-test"). */
  last?: { at: number; passed: boolean; step: number };
}

export interface RustStore { version: 1; rungs: Partial<Record<RustRung, RungRust>> }
```

**Per-rung evidence** (`rustEvidence(stats, rung, ctx)`) and re-test thresholds. The rung's own target is reused
throughout:

| Rung | Practice clock (last practised) | Fresh evidence = since `retest.from` | Judged when | Passes when |
|---|---|---|---|---|
| basic (+repair) | max `cellStats[*].lastAt` | Δ of `categories.hard/soft/pairs` right/wrong vs baseline | n ≥ 30 | right/n ≥ CATEGORY_TARGET (0.9) |
| count | last qualifying `countDrill` row date | qualifying rows dated ≥ from (`isQualifyingRun`, no self-report) | 5 rows (COUNT_RUNS_JUDGED) | ≥ 4 right (COUNT_RUNS_NEEDED) |
| tc | max(last deckEstimation, last trueCount row) | rows dated ≥ from, in each history | 10 and 10 | 8/10 each |
| deviations | max `quizSr[active].lastSeenAt` | Δ of Σ `perIndex[active]` right/wrong | n ≥ max(10, active.length) | ≥ INDEX_TARGET (0.9) |
| betramp | last betSizing row date | rows dated ≥ from | 10 | 8/10 |
| play | last session row date | session rows dated ≥ from with plays ≥ PLAY_MIN_GRADED | 1 such row | ≥ PLAY_TARGET (0.9) |

Dated histories are filtered by date, not by array offset, because `retention.ts` trims old rows. Counter deltas
are clamped at ≥ 0, since a backup restore or a Wrong-tap undo can make them shrink.

**State machine** (`advanceRust(store, ladderRaw, stats, ctx, now) → RustStore`, pure):

1. The rung passes live with no state: create `{ step: 0, provenAt: now }`. Existing users' passed rungs start their
   first 14 days at the first Home visit after deploy, with no backfill (A10).
2. `dueAt = dueAfterDays(max(provenAt, lastPractisedAt), RUST_INTERVALS_DAYS[min(step, 3)])`.
3. No open re-test and `now ≥ dueAt`: open one with `{ from: dueAt, baseline: evidence(now) }`. The rung is now
   **rusty**.
4. An open re-test whose fresh evidence is enough:
   - Pass: `step + 1`, `provenAt = now`, drop `retest`, drop `needsWork`. If it was a `needsWork` re-test, `step = 0`
     instead ("back to 14 days").
   - Fail: `step = 0`, `needsWork`, a new `retest` with `{ from: now, baseline: evidence(now) }`.
5. The rung fails its live rule while rusty: nothing extra. The ladder already shows it unpassed, which counts as
   needing work.

**Ladder integration** (`nextStep.ts`, small hooks):

- `LadderContext.rust?: RustStore`.
- `RungResult.rust?: 'rusty' | 'needsWork'`.
- `needsWork`: `passed = false`, with a re-test card. For example: title "Re-test: Running count", why "Missed its
  re-test: 3 of 5 paced runs right. Get 4 of your next 5." Start goes to the rung's `passedStart`; for deviations
  that is `reviewIndexes` = every active index.
- `rusty`: `passed` stays true, and `rust: 'rusty'` is added.
- New `CardKind 'retest'`. Step order: Review due (unchanged) first, then the earliest of {the current unpassed rung,
  the first rusty rung} by ladder position, then stale. A rusty rung outranks Keep it fresh.
- Re-test copy: "Passed 14 days ago and not practised since. 5 paced runs, 4 right, to keep it." The 30, 60 and 120
  day re-tests say "Passed its 30-day re-test …".

**Home / LadderCard:**

- `data-state="rusty"`, mark "↻", aria "N. label, rusty: re-test due", and a progress line "Re-test due".
- `needsWork` shows as current, as an unpassed rung does today.
- Home is the only writer: `useEffect(() => saveRust(next), [nextJson])` after `advanceRust`.
- `homeLadder` (`rungProgress.ts`) and `guidedStart.planInputFor` pass `rust: advanceRust(loadRust(), …)` in memory,
  so a drill's result line and the guided plan agree with Home without writing. The transition is pure, and dated
  rungs resolve from row dates, so every reader computes the same state.

**Guided plan.** In `planInputFor`, `rungsPassed[r.id] = r.passed && r.rust !== 'rusty'`. The segment holding a
rusty rung is then weak, gets double minutes, and is picked first in the 5-minute preset. That is "the guided plan
includes the re-test", with no change to `plan.ts`.

## ASSUMPTIONS

- **A1** Expiry is 12 h after the last write. A shoe from last night's drive is not resumed the next evening.
- **A2** "Finished" means the session is ended (End or New shoe). A cut-card reshuffle mid-session is not a finish:
  the table carries on into the next shoe and keeps being saved, which is the stamina case the brief protects.
- **A3** Mid-round death resumes at the last boundary, and the cut-off round is re-dealt from the same cards. The
  note says the count is where the last completed round left it. The alternative, re-shuffling only the unseen
  cards, keeps the count exact too; I chose exact order for determinism and testability.
- **A4** Only a table the page lost comes back. Leaving Play by choice (Home, Drills, profile editor) still deals a
  new shoe, as D3 defined it. Making those exits resume too is a one-line change to the clear in `noteNavigation`.
- **A5** Show chips is a Settings field drawn in the profile's Bankroll section, so toggling it never deals a new
  shoe. It is app-wide, not per profile.
- **A6** With `$ per unit` unset, chips assume $25 a unit, as the casino figures already do.
- **A7** Insurance is not drawn as chips. The pull-back figure covers the main bets only.
- **A8** Eyes-free Bet sizing propositions stay in units, spoken and shown. Chips are a visual aid.
- **A9** Payouts and pull-back are on Play only. The drill shows chips on its answer buttons and dollars in its
  verdict.
- **A10** 3B: rungs already passed at deploy start their first 14 days at the first Home visit after deploy, with no
  backfilled pass dates.
- **A11** 3B: rung 2 (weak cells and sweep) shares rung 1's re-test. Both are basic strategy, and Mastery has no
  dated failure to judge.
- **A12** 3B: one rust schedule for all profiles, since stats are global. The deviations evidence uses the active
  profile's index set.
- **A13** The resume note is visual only, not spoken. It shows after a tap on Play, so the screen is in hand.
- **A14** The selected chip and the hands choice (Table-local state) are not restored. The bet bar starts at 1 unit,
  as every new mount does.
